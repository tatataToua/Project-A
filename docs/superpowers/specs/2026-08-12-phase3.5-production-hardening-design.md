# Phase 3.5: Production Hardening

**Status:** Approved
**Phase:** New — inserted between Phase 3 (Intelligent Systems, done) and Phase 4
(Scaling, parked). This is an umbrella spec covering 7 sub-projects; each gets its own
implementation plan (and, where the work is non-trivial on its own, its own follow-up
spec) rather than one plan covering all of it.

## Why this exists

Prompted by a portfolio-advice video (Ash Vardhan, ex-Fireworks AI DevRel) identifying
five AI-engineering portfolio projects hiring managers actually respond to: production
RAG (hybrid retrieval + reranking + citation enforcement + eval/CI gating), local
small-model benchmarking, observability/monitoring, fine-tuning, and realtime
multimodal. See the full breakdown discussed in-session for how each mapped against
this repo's actual state.

Decision: two of the five (fine-tuning, realtime voice) are genuine departures from
this product's shape and are explicitly **out of scope** for this repo — they don't
extend the existing tenant-scoped text-chat RAG system, they'd sit beside it. The other
three map directly onto deepening what's already built:

- **Production RAG** → this repo already has chunking/embedding/pgvector/LangGraph
  retrieve-generate-critique. What's missing is exactly the "demo vs. production" gap
  the video describes: hybrid retrieval, reranking, citation enforcement, a golden eval
  set, and CI gating on quality.
- **Observability** → this repo already has a homegrown per-node JSONL tracer
  (`tracing.py`). What's missing is aggregation (P50/P95, cost/request, citation
  coverage, failure rate) — a natural extension, not a new system.
- **Local-model benchmarking** → the LLM client is already provider-swappable and
  verified against Ollama. What's missing is a rigorous multi-model comparison report.
  Folded in as a light bolt-on rather than a full sub-phase.

This phase is scoped as **portfolio/resume-signal work**: every sub-project should
produce something concrete and defensible (a metric, a report, a CI gate), consistent
with how `METRICS.md` already treats numbers as the deliverable, not just working code.

## Scope

**In scope** (7 sub-projects, in dependency order):
1. Hybrid retrieval (Postgres full-text search + existing pgvector)
2. Cross-encoder reranker (sentence-transformers)
3. Citation enforcement + explicit refusal
4. Golden eval set (per-tenant, Ragas) + CI gating (new GitHub Actions workflow)
5. Observability extension (aggregation on top of `chat_trace.log`)
6. Local-model benchmark report + classify-node structured output hardening
7. Prompt versioning (extract inline prompts to a dedicated module)

**Out of scope:** fine-tuning (LoRA/QLoRA/DPO) and a realtime voice/multimodal
assistant — noted as deliberate departures, not deferred work; revisit only if a
future session decides they're worth a *separate* repo/story. Phase 4 (Docker/AWS/
Redis) stays parked until this phase is done. Phase 5's PostHog analytics and
cost-governance/model-routing bullets are unchanged but now clearly build on this
phase's cost-per-request and eval groundwork.

**Explicitly not changing:** chunking stays heading-based (`chunking.py`) rather than
switching to the video's generic fixed-token-window-with-overlap advice — heading-based
chunking already fits this repo's structured markdown content better than advice aimed
at unstructured PDFs/docs.

## 1. Hybrid retrieval

`retrieval.py`'s `retrieve_chunks` currently does pure pgvector cosine-distance search.
Add a `tsvector` column to `EmbeddingChunk` (`models.py`) generated from `chunk_text`,
with a GIN index, populated at ingest time (`ingest.py`). At query time, run both:
- the existing vector search (top-N by cosine distance)
- a `ts_rank` full-text search over the same tenant's rows (top-N by rank)

Combine via reciprocal rank fusion (simple, no tuning of a blend weight) into a single
ranked list, still hard-filtered by `tenant_id` in both queries. Requires a migration
(this repo has no Alembic — `Base.metadata.create_all()` handles new columns on tables
that don't exist yet, but an *added* column on an existing table needs a one-off
`ALTER TABLE` step, documented in the implementation plan) and a re-ingest to backfill
`tsvector` for already-embedded content.

## 2. Reranker

New dependency: `sentence-transformers` (pulls `torch` — accepted cost, see decision
log below). Add a `reranking.py` module wrapping a small cross-encoder
(`cross-encoder/ms-marco-MiniLM-L-6-v2`, loaded once at import time like `app/llm.py`'s
client). `_retrieve_node` in `workflow.py` over-fetches (e.g. top-15 from hybrid
retrieval) and reranks down to the existing `RETRIEVAL_TOP_K`.

## 3. Citation enforcement + refusal

`retrieve_chunks` changes its return type from `list[str]` to a small `RetrievedChunk`
dataclass (`source_file`, `chunk_text`) so `_generate_node` can attribute claims to a
section. The critique node's existing groundedness check becomes the enforcement
point: today, a second failed critique still returns the generated answer as-is. New
behavior — if the retried answer fails critique again, `_generate_node`'s output is
replaced with an explicit decline (e.g. "We don't have that information — please ask
staff directly") before returning. This is the one behavior change to the existing
graph; everything else in this sub-project is additive.

## 4. Golden eval set + CI gating

Per-tenant, mirroring the existing content structure:
`docs/content/tenants/<slug>/eval/golden_qa.yaml` — a list of `{question, expected_answer,
source_files}` entries. Process: draft ~50-100 candidates per tenant from that tenant's
existing content, a human verifies/corrects before they're trusted as ground truth.
Starting tenant: Two Owls Tavern. This procedure is the repeatable part — onboarding a
future tenant means content → ingest → draft eval set → verify, same as any other
tenant setup step.

New `backend/scripts/eval_rag.py` (`--tenant <slug>`) runs Ragas (faithfulness,
context precision, context recall, answer relevancy) against the golden set, printing a
summary and exiting non-zero if the mean faithfulness score drops below a threshold
(start at 0.8, tune once real numbers exist).

New `.github/workflows/eval.yml` (first CI workflow in this repo): on PR, spins up a
Postgres+pgvector service container, runs `ingest.py` for the eval tenant(s), runs
`eval_rag.py` against the hosted Gemini free tier (API key from a repo secret) — a
build-blocking gate is only credible against a real provider, not a mock. Runs
alongside (not replacing) the existing `pytest` suite.

## 5. Observability extension

New `backend/scripts/trace_report.py`, reading `chat_trace.log` (already written by
`tracing.py` on every real request). Computes:
- Latency P50/P95 per node and end-to-end (not just the mean `bench_chat.py` already
  reports)
- Cost per request (token counts × provider pricing table, keyed off `GEMINI_MODEL`)
- Citation coverage (% of turns that did *not* hit the new refusal path from #3)
- Failure rate (% of turns where critique failed even after retry)

Output: a markdown report in the same spirit as `bench_chat.py` → `METRICS.md` — run
on demand, paste a summary row into the ledger. No new external service (Langfuse
considered and explicitly declined — the homegrown JSONL tracer already captures
everything needed; adding a hosted/self-hosted tool would be redundant infra for a
single-operator project at this stage).

## 6. Local-model benchmark + classify-node hardening

**Benchmark:** extend `bench_chat.py` (or a new `bench_models.py` alongside it) to loop
sequentially over 3 local Ollama models — `qwen2.5:7b-instruct` (existing baseline),
`llama3.2`, `mistral:7b` — pulling all three up front (disk space confirmed
non-constraining: 919GB free). Only one model is loaded in memory/VRAM at a time;
Ollama swaps automatically between sequential calls, so no concurrency concern. Records
tokens/sec, time-to-first-token, and (optionally) a GGUF quantization comparison (Q4 vs
Q5) if time allows. Same 30-50 fixed test-prompt set for all models for a fair
comparison. Output: a comparison table appended to `METRICS.md`, same pattern as the
existing baseline snapshot.

**Classify-node hardening:** `_classify_node` (`workflow.py`) currently asks for a
freeform category string and validates it against a hardcoded tuple. Convert to a
Pydantic-validated JSON schema response (`{"category": "menu" | "hours_location" |
"policies" | "general"}`), with one retry-on-invalid-output before falling back to
`"general"` — the same "constrained generation + validation + retry" pattern the video
calls out, applied to code that already exists rather than a standalone demo.

## 7. Prompt versioning

System prompts (classify, generate, critique) currently live as inline string literals
in `workflow.py`. Extract to `backend/app/prompts.py` (or a `prompts/` package if they
grow enough to warrant per-node files) as named constants/functions. Goal: prompt
changes show up as focused diffs distinct from logic changes, and `git blame` on a
prompt string gives a real history — matches the video's "prompts are part of your
system architecture" point. No versioning *system* (no DB table, no admin UI) — git
history is the version history, consistent with this repo's file-based-config
philosophy elsewhere (`instructions.txt`).

## Key decisions log

| Decision | Choice | Why |
|---|---|---|
| BM25 implementation | Postgres full-text search | No new dependency; stays in the DB layer beside pgvector; realistic for this corpus size |
| Reranker | sentence-transformers cross-encoder | Genuinely what "reranking" means in the industry; torch dependency accepted as a one-time cost |
| Eval framework | Ragas (not DeepEval, despite ROADMAP.md's old Phase 5 bullet) | Purpose-built RAG metrics (faithfulness, context precision/recall) match this project's shape better |
| Observability tool | Extend homegrown JSONL tracer | Already captures per-node timing/tokens/verdicts; adding Langfuse would be redundant infra at single-operator scale |
| Refusal on repeated critique failure | Explicit decline, not silent pass-through | This *is* citation enforcement — the video's core distinction between a demo and a production RAG system |
| Golden eval set authorship | Draft (from content) + human verify, per-tenant | Matches video's "manually verified" requirement while staying repeatable across future tenants |
| Local-model bench execution | All 3 models pulled up front, run sequentially | Only one model loaded in memory at a time regardless; disk space (919GB free) is a non-issue |

## Testing / success criteria

1. Existing `pytest` suite still passes (29/29 baseline) plus new tests for: hybrid
   retrieval tenant isolation, reranker ordering, refusal-path behavior, classify-node
   schema validation + retry.
2. `eval_rag.py --tenant two-owls-tavern` runs and reports faithfulness ≥ 0.8 against
   the verified golden set.
3. `.github/workflows/eval.yml` runs on a real PR and can be demonstrated failing when
   a deliberately-broken prompt is pushed (regression-gating actually works, not just
   exists).
4. `trace_report.py` produces P50/P95/cost/coverage/failure numbers from real traffic,
   pasted into `METRICS.md`.
5. `bench_models.py` produces a 3-model comparison table in `METRICS.md` with real
   tokens/sec and TTFT numbers.
6. A manual chat round-trip against Two Owls Tavern content still works end-to-end
   through the widget after all changes (no regression in the happy path).

## Non-goals (explicitly out of this phase)

- Fine-tuning (LoRA/QLoRA/DPO) — separate future project, not this repo.
- Realtime voice/multimodal assistant — separate future project, not this repo.
- Langfuse or any hosted tracing service.
- Alembic/formal migration tooling (the one schema change in #1 is handled as a
  documented one-off `ALTER TABLE`, consistent with how this repo has avoided migration
  tooling so far).
- Redis caching, AWS deployment, Docker (all still Phase 4, untouched).
